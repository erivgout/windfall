# QA inventory — 2026-10-09

This inventory records implementation coverage and acceptance requirements. It performs no functional verification and promotes no parity status. It snapshots the live working tree; concurrent QA agents may change tracker counts later. No GitHub CI or Actions were used.

## Tracker conventions and completion gate

`docs/parity/parity.json` is the source of truth. `PARITY.md` is generated with `node scripts/parity.mjs`; its current rendered counts lag the live JSON. The only supported statuses are `todo`, `in-progress`, `done`, and `wont-do`. There is no `verified-by-QA` status or evidence field. Keep implementation awaiting QA in `in-progress` and link durable dated QA evidence in notes. Preserve the existing two exclusions and their reasons.

Mark a row `done` only after every distinct behavior in its current summary has implementation and recorded acceptance evidence: exact commands/results, tested source snapshot, fresh generated artifacts where relevant, interaction/native integration, persistence/history/error/stale-request cases, and the row-specific audio/hardware/platform gates. A passing unit suite, enum registration, generic control panel, or mock browser does not establish the complete row. Missing scope remains `in-progress` even when the implemented subset passes. Existing done rows with new controls need regression evidence; their status is not evidence for new controls. Shared successor engines can close multiple rows only when each distinct contract is demonstrated. These rules follow IMPLEMENTATION-ROADMAP sections 2, 3 and 6.
